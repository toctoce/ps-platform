# Problem Authoring Guidelines

이 문서는 PS Platform 문제를 생성하거나 검수할 때 반드시 따르는 기준이다.

## 실제 문제 기반 원칙

- 문제는 반드시 실제 공개 문제를 기반으로 만든다.
- 문제 번호가 주어진 경우, 해당 번호의 실제 문제 조건을 외부 출처로 확인한 뒤 작성한다.
- BOJ와 solved.ac는 현재 사용할 수 없는 출처로 간주하고 직접 조회하지 않는다. 사용자가 다시 사용 가능하다고 명시하기 전까지 검수 대상에서 제외한다.
- BOJ 기반 문제는 Web Archive 스냅샷, 풀이 블로그, 문제 풀이 기록, 공개 코드의 입출력 설명 등 대체 출처를 사용한다.
- 기억, 유명 유형, 문제 제목, 풀이 패턴만으로 문제를 생성하지 않는다.
- 출처로 확인하지 못한 입력 형식, 출력 형식, 제한, 예제, 핵심 조건은 추정해서 쓰지 않는다.
- 확인이 불가능하면 draft를 만들지 말고 확인 불가 상태를 먼저 보고한다.
- 원문 문장을 복사하지 않는다. 확인한 조건을 바탕으로 플랫폼용 한국어 설명을 새로 작성한다.

## 출처 확인 기준

문제 생성 전 다음 항목을 실제 출처와 대조한다.

BOJ 번호 기반 문제를 검수할 때 우선순위는 다음과 같다.

1. Web Archive에 남아 있는 BOJ 문제 스냅샷
2. 입출력, 제한, 예제가 명확히 적힌 풀이 블로그나 공개 풀이 기록
3. 입력 형식과 조건을 주석 또는 설명으로 포함한 공개 코드 저장소

BOJ 또는 solved.ac 직접 페이지는 확인 시도하지 않는다.

- 문제 제목과 번호
- 입력 형식
- 출력 형식
- 입력 제한
- 예제 입력과 예제 출력
- 예외 조건과 불가능한 경우의 출력
- 정렬 기준, 사전순 기준, 동점 처리
- 수 범위와 필요한 자료형
- 여러 정답이 가능한지 여부
- 시간 제한을 결정할 핵심 제약

출처가 여러 개일 때 서로 충돌하면 임의로 고르지 않는다. 충돌 내용을 사용자에게 보고하고 결정이 필요한 부분을 명확히 한다.

## 문제 설명 작성 기준

- 설명은 초보자가 문제 상황과 목표를 바로 이해할 수 있게 쓴다.
- 문장을 잘게 끊어 딱딱하게 나열하지 말고, 하나의 문제처럼 자연스럽게 이어지게 쓴다.
- 너무 짧아서 핵심 규칙이나 동작이 빠지면 반드시 보강한다.
- 문제의 핵심 동작은 빠뜨리지 않는다. 예를 들어 스택 문제에서는 어떤 값으로 수열을 만드는지, 시뮬레이션 문제에서는 무엇이 언제 변하는지 명확히 쓴다.
- 시각적 구조가 중요한 문제는 그림이 없어도 이해되도록 방향, 위치, 포함 관계, 이동 방식 등을 말로 설명한다.
- 불가능한 경우, 여러 답 처리, 동점 처리, 사전순, 기호 순서 같은 판정 기준은 문제 설명이나 출력 설명에 명확히 쓴다.
- 실제 문제에는 없지만 플랫폼용으로 바꾼 출력/입력 형식이 있으면 그 변형 조건이 설명과 예제에 일관되게 드러나야 한다.
- 의미 없거나 당연한 표현은 제거한다. 예: 이미 알 수 있는 "높이가 다른 또는 같은", 반복되는 "원형으로" 같은 문장.
- 같은 내용을 중복해서 말하지 않는다.
- 용어가 어색하면 자연스러운 표현을 우선한다. 예: 꼭 필요한 경우가 아니면 조어를 피하고 "괄호로 이루어진 문자열"처럼 쓴다.
- 필요한 용어는 처음 나올 때 정의하고, 이후에는 짧게 사용한다.
- 문제 설명에는 구현 전략이나 정답 힌트를 직접 노출하지 않는다.
- 입력 범위만으로 알 수 있는 자료형 힌트는 설명에 쓰지 않는다. 예: "32비트 정수 범위를 넘을 수 있다" 같은 문장은 필요한 경우 제한과 풀이에서 다룬다.
- 입력 설명, 출력 설명, 예제, 테스트가 문제 설명과 서로 어긋나면 안 된다.
- 입력 제한의 큰 수에는 세 자리 단위 쉼표를 넣는다. 예: `1 <= N <= 100,000`
- 플랫폼용 제한은 가능하면 `1,000,000,000`처럼 읽기 쉬운 십진수 경계로 정한다. `2,147,483,647`처럼 구현 자료형에서 나온 경계값은 문제의 핵심 조건이 아닌 이상 피한다.
- 출력이 `YES`/`NO`류라면 플랫폼 스타일에 맞는 출력이 더 나은지 사용자와 논의한다.
- 복잡한 조건은 번호나 문단을 나누어 명확히 한다.

## 예제 설명 기준

- 예제 설명은 사용자가 왜 해당 출력이 나오는지 헷갈릴 때만 작성한다.
- 단순 계산이나 출력 반복은 설명하지 않는다.
- 예제 설명이 필요하면 실제 중간 과정, 선택 이유, 제외되는 값 등을 보여준다.
- 불가능한 경우, 예외 출력, 특수 규칙이 있는 예제는 설명을 붙이는 편이 좋다.
- 예제 설명이 틀리면 문제 신뢰도가 크게 떨어지므로 expectedOutput과 따로 대조한다.

## 테스트 케이스 기준

- 기존 케이스를 대체하지 말고, 사용자가 추가를 요청하면 새 케이스를 추가한다.
- 작은 경계값과 큰 경계값을 모두 포함한다.
- 자료형 경계가 있으면 해당 자료형을 넘는 입력이나 출력을 포함한다.
- 중복, 모두 같은 값, 불가능한 경우, 정렬 역순, 극단적인 위치 등 오답이 잘 나는 케이스를 넣는다.
- 모든 expectedOutput은 기준 구현이나 별도 계산으로 재검산한다.
- 계산을 추정하지 않는다. 계산 실수 가능성이 있으면 작은 검증 스크립트를 만들어 대조한다.

## 카테고리 기준

- `docs/problem-categories.md`에 있는 카테고리만 사용한다.
- 사용자가 명시한 카테고리는 반드시 포함한다.
- 추가 카테고리가 필요해 보이면, 새 카테고리를 만들기 전 사용자에게 말한다.
- 이미 존재하는 카테고리를 추가하는 것은 가능하지만, 왜 필요한지 검수 결과에 간단히 언급한다.

## 난이도와 제한 기준

- 사용자가 난이도 매핑을 준 경우 그 매핑을 따른다.
- 시간 제한은 입력 범위와 의도한 풀이를 함께 보고 정한다.
- 시간 제한을 낮추려면 입력 범위를 줄이거나 풀이 설명을 더 효율적인 방식으로 맞춘다.
- 입력 범위를 키울 때는 기존 풀이와 테스트가 여전히 맞는지 확인한다.
- 실제 문제의 제한이 자료형 경계값일 때는 플랫폼용 십진수 제한으로 바꿔도 풀이 의도가 유지되는지 확인한다.
- Java 기준으로 `int`를 넘는 입력이나 출력이 가능하면 `long` 사용 필요성을 풀이에 반영한다.

## 검수 체크리스트

검수할 때는 다음을 우선 확인한다.

- 실제 문제 조건과 다른 부분이 없는가
- 입력 형식이 플랫폼 문제 설명과 예제에 일관되게 반영됐는가
- 출력 형식이 정확한가
- 불가능한 경우의 출력이 명확한가
- 예제 설명이 맞고, 너무 과하거나 너무 부족하지 않은가
- 테스트 케이스가 기존 케이스를 덮어쓰지 않고 충분히 추가됐는가
- 큰 수, 경계값, 자료형 문제가 테스트에 포함됐는가
- 카테고리가 정확한가
- 제한과 시간 제한이 의도한 풀이와 맞는가
- JSON 검증과 expectedOutput 재계산을 통과했는가

## 작업 보고 기준

완료 보고에는 다음을 포함한다.

- 어떤 파일을 만들거나 수정했는지
- 실제 출처 확인 여부
- 검증 명령 결과
- expectedOutput을 어떤 방식으로 재계산했는지
- 확인하지 못한 부분이나 남은 위험
