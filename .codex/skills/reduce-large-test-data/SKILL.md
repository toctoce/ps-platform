# 대형 테스트 데이터 축소

## 핵심 원칙

- 데이터가 너무 큰 경우, 작은 데이터 두 개로 대체한다.
- 대체하는 작은 데이터도 충분히 커야 한다. 입력 제한의 최댓값일 필요는 없지만 의도한 알고리즘의 성능과 구현 오류를 확인할 수 있을 만큼 적당히 큰 규모로 만든다.
- 대체 데이터는 랜덤해야 하며 테스트 케이스로서 의미가 있어야 한다. 같은 값의 단순 반복이나 규칙 하나만으로 정답이 결정되는 데이터 두 개를 만들지 않는다.
- 난수 시드를 고정하거나 생성 규칙을 기록해 데이터를 재현할 수 있게 한다.
- 문제의 입력 제한, 정답 정의, 난이도와 의도한 알고리즘은 바꾸지 않는다.

## 작업 절차

1. 한 번에 크기가 큰 문제 1~2개만 선택한다.
2. 파일 전체 크기와 각 `testCases` 항목의 입력·출력 크기를 측정해 용량을 차지하는 테스트를 찾는다.
3. 예제와 유효한 작은 테스트는 유지한다. 과도하게 큰 테스트만 제거하고, 제거한 테스트 하나마다 작은 대형 테스트 두 개를 같은 위치에 넣는다.
4. 알려진 요청 크기 제한보다 충분한 여유가 생기도록 파일을 줄인다. 제한을 모르면 최종 JSON을 1MB 미만으로 만드는 것을 우선 검토하되, 테스트 가치가 훼손되면 사용자에게 적절한 목표 크기를 보고한다.
5. 대체 테스트마다 크기, 값 분포, 정렬 상태, 장애물 또는 그래프 구조 등 문제에 맞는 특성을 다르게 만든다.
6. 모든 `expectedOutput`을 기준 구현이나 독립 계산으로 다시 구한다. 생성 코드에서 계산한 결과만 믿지 말고 별도 검증 로직으로 한 번 더 대조한다.
7. JSON 검증을 실행하고 변경 전후 파일 크기, 교체한 테스트 수, 새 테스트 규모를 보고한다.

## 데이터 생성 기준

- 입력 제한에 비해 지나치게 작은 장난감 데이터로 축소하지 않는다.
- 최댓값, 모두 같은 값, 완전 정렬처럼 한 가지 극단만 반복하지 않는다.
- 서로 다른 고정 시드를 사용해 최소 두 데이터의 값과 구조가 실제로 달라지게 한다.
- 중복 허용 여부, 좌표 고유성, 연결성, 목표 개수 등 입력의 모든 조건을 생성 후 검증한다.
- 랜덤 데이터만으로 놓치기 쉬운 핵심 경계 테스트가 기존에 있다면 유지한다.
- 큰 입력과 큰 출력이 함께 발생하는 문제는 둘의 합을 기준으로 JSON 크기를 판단한다.

## 완료 기준

- 과도하게 큰 테스트 하나가 의미 있는 작은 대형 테스트 두 개로 교체되어 있다.
- 두 테스트가 적당히 크고 서로 다른 랜덤 특성을 가진다.
- 입력 조건과 `expectedOutput`이 독립 검증을 통과한다.
- 최종 파일이 목표 요청 크기 안에 들어간다.
- 사용자가 명시적으로 요청하지 않으면 문제 데이터는 커밋하지 않는다.
